Distributed Load Balancer with Consistent Hashing & Docker Replicas

Course: B.Tech Cloud Computing • Technologies: Python 3.10, Flask, Docker, Consistent Hashing • Dashboard: http://localhost:6000/

1. What is the Problem?

When web services grow, handling high traffic on a single server causes three critical problems:

  • Single Point of Failure (SPOF) & Server Overload: If all clients connect to only one server, that server quickly runs out of CPU and memory. When it crashes, the entire service goes completely offline.
  • The Flaw of Traditional Modulo Load Balancing (Hash % N): Naive systems divide requests across $N$ servers using remainder arithmetic: Server = Request_ID % N. When you add a 4th server ($N=3 \to 4$), the divisor changes for every key. Almost 100% of all requests are remapped to completely different servers. This wipes out server caches, overloads backend databases, and causes system crashes.
  • Silent Server Crashes (No Fault Tolerance): If one server replica crashes quietly, a basic system does not notice and keeps routing requests to the dead server, returning errors to users.

2. How Are We Solving It?

We built a Distributed Load Balancer that coordinates multiple server replicas using Consistent Hashing and Docker containerization:

The Problem How We Solve It Technical Mechanism
Single Point of Failure Server Replicas (Docker) Multiple identical server replicas (Server-1, Server-2, Server-3) run in isolated Docker containers.
Modulo Remapping Flaw Consistent Hashing Servers and requests are mapped onto a 512-slot circular ring with virtual nodes ($K=20$). Adding a server only moves $\sim 1/N$ of keys!
Silent Server Crashes Heartbeat Fault Detection The load balancer probes /heartbeat every 30s. Dead containers are automatically pruned and deleted via docker rm -f.
Traffic Spikes Dynamic Horizontal Scaling REST endpoints (/add, /rm) spin up or terminate Docker containers dynamically in seconds.

4. Consistent Hashing Explained Simply

Instead of basic modulo division (Request % N), Consistent Hashing maps both servers and requests onto a circular ring of 512 slots (indices 0 to 511):

  • Virtual Nodes (K = 20): To prevent one server from receiving too many requests, each server replica is assigned 20 virtual positions around the ring using: 
    Φ(i, j) = (i² + j² + 2j + 25) % 512
  • Clockwise Routing: When an incoming request arrives, its Request ID is hashed to a slot using: 
    H(i) = (i² + 2i + 17) % 512
    The load balancer travels clockwise along the ring until it hits the first server replica. That server handles the request.
  • Why Consistent Hashing is Superior: When a new server is added, only a small slice of keys is remapped to the new server. All other servers keep their existing requests, preserving cache affinity.

6. Fault Tolerance & Self-Healing

  1. Failure Simulation: A container crashes or is stopped manually (e.g. Server-2).
  2. Heartbeat Detection: Every 30 seconds, the load balancer sends an HTTP request to http://<server>:5000/heartbeat.
  3. Dead Container Removal: Server-2 fails the heartbeat check.
  4. Automated Recovery Actions:
    • Marks Server-2 as unhealthy.
    • Purges its virtual nodes from the consistent hash ring.
    • Executes docker rm -f Server-2 to clean up the dead container.
    • Reroutes subsequent traffic to Server-1 and Server-3 with zero client downtime.

7. Viva / Presentation Q&A Cheat Sheet

Q1: What is a Load Balancer?
A: A system that distributes incoming client requests across multiple backend server replicas so no single server becomes a bottleneck.
Q2: What is the main problem with standard Modulo Load Balancing (Hash % N)?
A: When you add or remove a server (N changes), almost 100% of all request keys are remapped, destroying caches and overloading databases. Consistent Hashing solves this by only moving ~1/N of keys.
Q3: What are Virtual Nodes in Consistent Hashing?
A: Instead of placing each physical server at only 1 spot on the ring, we place it at K=20 virtual positions. This ensures traffic is distributed evenly and prevents clustering.
Q4: Why use Docker containers in this project?
A: Docker allows us to run multiple isolated server replicas on a single machine, each with its own network identity, port, and environment variables.
Q5: How does Heartbeat Fault Tolerance work?
A: The load balancer polls /heartbeat on every server replica every 30 seconds. If a replica stops responding, it is automatically removed from the consistent hash ring and its container is deleted.
